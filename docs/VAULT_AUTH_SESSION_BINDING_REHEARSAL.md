# Liaison des capacités du coffre à Auth — répétition isolée

Le SQL candidat n'est pas une migration canonique et ne doit pas être appliqué directement en production. Le workflow sans secrets génère un fichier de migration avec le CLI, le rejoue localement et exécute 28 assertions pgTAP avec des identités synthétiques.

La capacité est liée à l'identifiant de la session Auth vérifiée par l'Edge. Les nouvelles RPC serveur verrouillent et vérifient la session Auth vivante (propriétaire, AAL2, expiration) et la capacité d'origine dans la même transaction. Les ouvertures d'un compte sont sérialisées. Les anciennes capacités sont révoquées sans effacer les entrées ni l'audit. Les six anciennes RPC perdent leurs droits d'exécution pour les clients et service_role; les nouvelles RPC ne sont exécutables que par service_role parmi ces rôles.

Limites : aucun changement des Edge Functions dans ce lot. L'intégration canonique devra adapter les six appels Edge pour transmettre exclusivement le session_id du JWT déjà vérifié, mettre à jour les contrats historiques et tester deux sessions AAL2 du même compte via HTTP. La migration et l'Edge doivent être déployées de manière coordonnée pendant une fenêtre de maintenance : la version ancienne de l'Edge sera refusée après migration. Ne pas restaurer les droits legacy pour contourner ce refus. Vérifier les droits effectifs, les verrous et les interactions avec la révocation Auth en environnement isolé avant déploiement. Le contrôle ne protège pas contre un serveur entièrement compromis. Aucun identifiant Auth n'est publié dans les réponses du coffre. Aucune écriture production ni modification du ledger dans ce lot.

Les comptes synthétiques incluent les métadonnées obligatoires d'inscription; le trigger de création de compte reste actif. Les tests vérifient aussi les refus d'exécution des anciens RPC sous le rôle SQL service_role et des nouveaux RPC sous les rôles authenticated et anon, au-delà de la simulation des claims JWT. Les résultats de cette répétition ne constituent pas une validation en production.

## Intégration canonique proposée

La répétition #1351 a réussi 28/28 assertions. Le fichier `20261128082928_sinjira_vault_auth_session_binding.sql` reprend le blob exact testé (SHA-256 `f9d47832451382eefbec3d3d859b05f72d1696dec1a5d312f2b048ff31b494dd`). Le lot suivant ajoute les six appels Edge liés au JWT et les tests HTTP intersessions. Le workflow rejoue désormais la migration canonique avec contrôle d'empreinte. Le manifeste futur compte 19 migrations; l'historique de production reste inchangé et divergent. Ne pas lancer de synchronisation globale pour ce correctif. Déploiement coordonné et approbation explicite requis; aucun succès en production n'est revendiqué.
