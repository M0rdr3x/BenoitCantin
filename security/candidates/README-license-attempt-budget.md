# Quota individuel d'activation — candidat NO-GO
Cinq tentatives de codes textuels de longueur valide par compte authentifié sur une fenêtre de dix minutes démarrant à la première tentative. Un appel RPC distinct comptabilise avant hachage/activation, donc un échec métier ne rembourse pas le quota. L'upsert atomique borne la concurrence, verrou 250 ms ; la fonction est SECURITY INVOKER, accès service_role seulement et table privée RLS. Une ligne par compte ayant tenté, supprimée par cascade lors de la suppression du compte. Aucun code, hash de licence, IP ou historique détaillé enregistré. L'UUID interne est une donnée personnelle pseudonyme, pas anonyme : prévoir purge des compteurs expirés sous contrôle serveur et politique de conservation courte avant déploiement.
Le diagnostic health reste minimal et authentifié ; il n'utilise pas ce quota d'activation. Les abus de health/auth, comptes multiples, attaques réseau et tentatives malformées ne sont pas couverts. Plafond provisoire à valider en staging; fenêtre fixe, pas une vraie fenêtre glissante.
Le RPC n'existe pas sur Supabase actif. Ne pas fusionner ni déployer avant migration canonique réconciliée, validation des droits, tests HTTP réels, concurrence multi-transactions, maintien du parcours légitime et rollback. Le SQL candidat reste hors migrations avec ROLLBACK. Les tests n'utilisent que des comptes fictifs dans une base locale.

## Plafond collectif et correction des fixtures — 24 novembre 2026
Le plafond individuel reste de cinq tentatives par dix minutes. Un second compteur global, une ligne fixe sans identifiant individuel, limite à 60 admissions par fenêtre d'une minute. Les deux contrôles sont atomiques dans le même RPC ; une demande individuellement refusée ne consomme pas le budget collectif, tandis qu'une demande collectivement refusée consomme le budget individuel. Une erreur de verrou annule la transaction du contrôle. Une saturation collective peut néanmoins gêner les utilisateurs légitimes : seuil à calibrer, alerte agrégée et WAF nécessaires. Le compteur global ne remplace pas un challenge antibot et n'est pas une limite sur les appels Auth/health eux-mêmes.
La CI précédente a échoué sur BIRTH_DATE_REQUIRED lors de la création des fixtures Auth. Les comptes fictifs sont maintenant renseignés avec les métadonnées minimales déjà utilisées dans les essais locaux de révocation, sans désactiver le trigger. Les assertions supplémentaires testent le dernier droit collectif, le refus inter-compte et la réinitialisation de fenêtre. Aucun compte réel, aucune migration active, aucune modification de production.
